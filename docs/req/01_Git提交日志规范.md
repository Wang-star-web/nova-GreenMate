## 一、为什么这份材料"补不回来"

其他四份材料都能在截止前一天加班做出来。这一份不行。

提交日志的价值在于**时间分布**：11 月 17 日一天提交 40 次，和 10 月 26 日到 11 月 16 日每天提交 2 次，前者的信息量是零，后者是完整证据。

所以这条只有一句话：**今天不动手，明天就少一天。** 改时间戳等于伪造，一旦被问出来，前面所有材料一起作废。

## 二、提交信息怎么写

### 格式

```text
<类型>(<范围>): <做了什么>

<为什么这么做 / 解决了什么问题>（可选，但强烈建议写）
```

### 类型对照

| 类型 | 用在哪 | 示例 |
| --- | --- | --- |
| `feat` | 新增功能 | `feat(analysis): 增加资料不足时的拒答分支` |
| `fix` | 修复问题 | `fix(export): 修复导出时区偏移 8 小时` |
| `refactor` | 结构调整，行为不变 | `refactor(state): 把事件状态收敛到单一 reducer` |
| `docs` | 文档 | `docs(readme): 补充最小可跑模式的启动步骤` |
| `test` | 测试 | `test(rule): 补阈值两侧的边界用例` |
| `chore` | 配置、依赖 | `chore(deps): 锁定 vite 到 8.3.4` |

### 正反例

| 反例 | 正例 |
| --- | --- |
| `update` | `feat(weather): 天气请求失败时显示 TIMEOUT 而非空白` |
| `fix bug` | `fix(mqtt): 断线重连后重复订阅导致消息翻倍` |
| `1` | `chore: 初始化项目骨架` |
| `修改` | `fix(priority): 未关闭事件未参与排序权重` |
| `提交` | — |
| `又改了一版` | `refactor(ui): 拆出 PriorityCard 组件，去掉重复计算` |

> **判据：不看 diff 也能知道这次改了什么、为什么改。** 做不到就重写。

## 三、什么算"一次提交"

一条判据：**能不能用一句话说完，且这句话里只有一个动作。**

| 应该分开提交的 | 不该混在一起 |
| --- | --- |
| 加功能 / 修 bug / 调格式 / 改文档 | 同一个提交里既有新功能又有重构又有格式调整 |
| 一个模块的改动 | 一次性改 6 个模块的 300 行 |

**不要为了凑数量把一次改动拆成 5 次。** 拆得假（比如同一个文件拆成"加了一行注释""加了第二行注释"），评委会反感，效果比不拆更差。

## 四、交付内容

```text
01_Git提交日志/
├── commit-index.md          ← 索引表（最重要）
├── git-log-graph.txt        ← git log --graph --oneline --all
└── git-log-oneline.txt      ← git log --date=short --pretty=format:"%h %ad %s"
```

生成命令：

```bash
git log --graph --oneline --all --date=short > 01_Git提交日志/git-log-graph.txt
git log --date=short --pretty=format:"%h %ad %s" > 01_Git提交日志/git-log-oneline.txt
```

## 五、`commit-index.md` 模板

这是整套材料里性价比最高的一个文件：**它把三份材料串起来。**

```markdown
# 提交索引

**仓库：** <地址>
**分支：** <main / master>
**标签：** <v1.0-final> → 指向 `<commit hash>`
**首次提交：** <YYYY-MM-DD>
**提交总数：** <N> 次，跨 <N> 天

## 关键提交与证据对应

| # | 提交 | 日期 | 做了什么 | 对话案例 | 技术文档 |
| --- | --- | --- | --- | --- | --- |
| 1 | `a1b2c3d` | 10-26 | 项目骨架 + MQTT 接入 | — | 2.1 |
| 2 | `b2c3d4e` | 10-28 | 规则判断与 Priority 计算 | `01_...` | 3.2 |
| 3 | `c3d4e5f` | 10-30 | 外部服务失败时的降级分支 | `03_...` | 3.4 |
| ... | | | | | |

## 提交节奏说明

<如果有集中的批量提交，在这里主动说明。例如：>

本仓库自 2026-10-26 建立，此后按功能模块提交。
10 月 30 日有 4 条提交间隔在 10 秒内，原因是在本地连续完成同一模块的 4 处改动后一次性推送。

## 未提交的内容及原因

| 内容 | 原因 |
| --- | --- |
| <模型文件 / 测试数据 / 大体积图片> | 体积超过仓库限制，通过 <下载地址 / 生成命令> 提供 |
```

> **"未提交的内容及原因"这一张表不能省。** 评委 clone 下来发现缺文件、又找不到说明，会认为你交付不完整。

## 六、三种现状，各自的处理方式

### 现状 A：还没有 Git 仓库（立刻要做）

```bash
cd <项目目录>
git init
git add -A          # ⚠️ 先别执行，看下面的检查
git commit -m "chore: 导入既有代码"

# 然后按模块往回拆：不要只是一个巨大的 commit
```

#### ⚠️ `git add -A` 之前先查 `.gitignore`（这一步省不得）

`git add -A` 会把目录里**所有**东西加进仓库。这里有三个后果，都是灾难性的：

| 混进去的东西 | 后果 |
| --- | --- |
| `.env`、密钥文件 | **密钥泄露到公开仓库**。GitHub 上的爬虫几分钟内就会扫到，可能产生真实费用 |
| `node_modules/`、`venv/`、`dist/` | 一次提交几万个文件，仓库变成几百 MB，评委 clone 要半小时 |
| `.db`、模型权重、大图 | 超过仓库限制，推不上去；或者推上去了打不开 |

**检查三条命令：**

```bash
cat .gitignore                       # 没有这个文件就先建一个
git add -A --dry-run | wc -l         # 预览会加多少个文件，超过 200 行基本有问题
git status --short | grep -i "\.env\|key\|secret"   # 有没有敏感文件混进来
```

`.gitignore` 至少要包含：

```gitignore
.env
.env.local
*.key
*.pem
node_modules/
venv/
__pycache__/
*.db
dist/
```

**万一 `.env` 已经提交上去了：**

```bash
git rm --cached .env      # 只从仓库移除，本地文件保留
git commit -m "chore(security): 移除误提交的环境变量文件"
```

**注意：这不会把 `.env` 从历史里删掉**，别人 checkout 旧提交仍能看到。所以真正的处理是**立刻去平台把那个密钥作废重发**。这一步比改代码重要得多。

**另外**：只有一个初始化提交是可以接受的（因为代码是既有成果），但**必须接着补真实的分段提交**。如果到交稿时 log 里仍然只有一条 `initial commit`，这一项就是零分。

更稳的做法：初始化之后，把接下来每一次真实的改动都拆成独立提交，**平均每天 1 次左右**。从现在到截止日按天数算，正常能攒出 20 条以上真实记录。

### 现状 B：有仓库但提交集中在一两天

不改历史。做两件事：
1. 在 `commit-index.md` 的"提交节奏说明"里如实写清原因（例如"前期在本地开发，10 月 1 日统一推送"）
2. **从今天起**正常提交，让后半段有真实节奏

**绝对不要**：`git rebase` 改时间戳、`--date` 伪造、删掉旧提交重建。这三件事做出来，比集中提交严重得多。

### 现状 C：有历史但提交信息全是 `update`

不改历史。做一件事：在 `commit-index.md` 里**重建一份可读索引**，把每个 hash 对应到什么功能写清楚。

这样做拿不到满分（原始信息质量就那样），但比什么都不做强，而且诚实。

## 七、红线（做了就不是扣分的问题了）

| 行为 | 后果 |
| --- | --- |
| 改提交时间戳（`--date` / `GIT_COMMITTER_DATE`） | 伪造证据 |
| `rebase` 重排历史以制造"分散提交" | 伪造证据 |
| 删掉旧仓库重建，让 log 看起来干净 | 伪造证据，且丢失真实历史 |
| 用脚本批量生成空提交 | 一眼可见（无文件变更） |
| 提交信息与实际 diff 不符 | 一旦被抽查，全盘失信 |

> **一句话：可以少，不能假。** 20 条真实提交 > 200 条伪造提交。

## 八、交稿前自检

- [ ] 首末提交跨度 ≥ 15 天，且覆盖 ≥ 10 个不同日期（`git log --format=%ad --date=short | sort -u` 可数不同日期）
- [ ] 提交信息里没有 `update` / `fix` / `1` / `修改` 这种
- [ ] `commit-index.md` 的三列对应关系已填满
- [ ] 标签指向的 Commit 与文档里写的一致（用 `git rev-parse <tag>` 核对）
- [ ] "未提交的内容"已列出并给了获取方式
- [ ] 用**退出登录的浏览器**打开仓库地址，能看到 README 与提交记录（仓库须 Public；私有则已给评审账号开权限）
- [ ] 没有改过任何历史
