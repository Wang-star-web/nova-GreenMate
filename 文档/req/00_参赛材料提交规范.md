## 零、学生从哪开始（先看这 5 行）

六份文件加起来 1600 多行，不要按顺序读完再看手。按下面的顺序动：

1. 读本文件第二章，建 5 个空文件夹（`01` 到 `05`），30 分钟
2. **今天**执行 `01_Git提交日志规范` 第六章的「现状 A」——没有仓库的，这是唯一一件"今天不做就永久损失一天"的事

> 判断标准很简单：**凡是事后能补的，晚做；凡是过了就没了（提交历史、原始对话、当时的报错），当场做。**

## 一、先定容器，再填内容

大部分参赛包的问题不是"写得不好"，而是**评委找不到**。

评委的真实动作是：解压 → 看目录 → 找 5 样东西 → 逐个判"有 / 没有"。找不到就按"没有"计。所以：

> **目录结构本身就是得分项，不是排版问题。**

这份规范只做四件事：
1. 定一个固定目录结构（所有人一致）
2. 定 5 项材料的交付规格（量、格式、下限）
3. 定一条证据对齐原则（提交 ↔ 对话 ↔ 文档）
4. 给一个提交前自检表

## 二、标准目录结构

```text
传智杯-参赛材料-<姓名>-<学号>/
├── 00_提交说明.md
├── 01_Git提交日志/
│   ├── commit-index.md
│   ├── git-log-graph.txt
│   └── git-log-oneline.txt
├── 02_AI对话快照/
│   ├── 索引.md
│   ├── 01_<案例名>/
│   │   ├── 说明.md
│   │   ├── 01-我的原始提问.png
│   │   ├── 02-AI第一次的方案.png
│   │   ├── 03-我发现的问题.md
│   │   ├── 04-我的纠偏指令.png
│   │   └── 05-验证结果.png
│   ├── 02_<案例名>/
│   └── 03_<案例名>/
├── 03_复现指南/
│   ├── README.md
│   ├── .env.example
│   └── 10分钟实测记录.md
├── 04_演示视频/
│   ├── 演示视频.mp4
│   ├── 视频脚本.md
│   └── 字幕.srt（可选）
├── 05_技术文档/
│   └── 技术文档.pdf
└── 06_源码说明.md
```

**为什么是这个顺序：** `01` 到 `05` 正好是章程列的 5 项交付物顺序。评委按章程核对，你的编号和他的清单一一对上，不用思考。

`06_源码说明.md` 里只放四件东西：仓库地址、分支名、标签名、**仓库可见性**（Public／已授权评审账号 `<账号>`）。**不要把源码压缩包塞进来**，那是仓库的事，塞进来会被认为不理解"提交仓库"这个要求。

> ⚠️ `03_复现指南/.env.example` 是**副本**。真正的 `.env.example` 必须放在**仓库根目录并提交**，否则评委 clone 下来没有模板可用。两处都要有，内容一致。

## 三、命名规则（5 条，所有人一致）

| 规则 | 示例 | 反例 |
| --- | --- | --- |
| 1. 顶层目录两位数字前缀 | `02_AI对话快照` | `AI对话` |
| 2. 用中文全称，不用拼音和缩写 | `05_技术文档` | `05_techdoc` / `05_js` |
| 3. 编号与名称之间用连字符，名称内部用下划线，**一律不用空格** | `01-我的原始提问.png` | `01 我的原始提问.png` |
| 4. 文件不带版本后缀 | `技术文档.pdf` | `技术文档-最终版-改2.pdf` |
| 5. 顶层文件夹带姓名学号 | `传智杯-参赛材料-张三-25051F` | `新建文件夹` |

**第 3 条不是强迫症**：文件名带空格，在部分解压工具和在线预览里会变成 `%20`，评委点开可能失败。
**第 4 条不是洁癖**：出现"最终版""修改版"意味着你自己都不确定哪个是最终，评委会直接怀疑材料完整性。

## 四、5 项材料的交付规格

> 下表的"硬性下限"是**本团队的验收线**，不是章程原文。章程只规定形式（3 个案例、5–8 分钟、≤30 页），具体数量下限由我们自己定，目的是留出安全余量。

### 材料 1 · Git 提交日志

| 项 | 要求 |
| --- | --- |
| 交付内容 | `01_Git提交日志/` 下 3 个文件：`commit-index.md`、`git-log-graph.txt`、`git-log-oneline.txt` |
| 格式 | 文本 + Markdown |
| **可见性** | 仓库须设为 **Public**；若必须私有，须提前给评审账号开权限。交稿前用**退出登录的浏览器**打开仓库地址，确认能看到 README 与提交记录 |
| **硬性下限** | 提交次数 ≥ 20；首末提交跨度 ≥ 15 天，且覆盖 ≥ 10 个不同日期；每次提交对应一个功能或一个修复 |
| 禁止 | 一次 initial commit 包含全部功能；提交信息为 `update` / `fix` / `1` / `.` |
| 验收标准 | ① `git log` 的时间分布不是同一天堆完；② `commit-index.md` 能把关键提交对应到对话快照编号 |
| 拿不出来怎么办 | 时间跨度已经不够的，**不能改时间戳**（等于伪造）。如实提交现有历史，在 `commit-index.md` 顶部写明"本仓库自 X 月 X 日建立"，把力气转到能积累的部分 |

> 详细规范见同目录 `01_Git提交日志规范.md`。

### 材料 2 · AI 对话历史快照

| 项 | 要求 |
| --- | --- |
| 交付内容 | `02_AI对话快照/` 下 3 个案例目录，每个含 4 张截图（`01`/`02`/`04`/`05`）+ `03-我发现的问题.md` + `说明.md` |
| 格式 | PNG（截图优先用 PNG）+ Markdown（文字），截图必须是图片，**不能是文字复述** |
| **硬性下限** | 3 个案例；每个案例必须包含"原始提问 → AI 第一次方案 → 我发现的问题 → 我的纠偏 → 验证结果"五段 |
| 禁止 | 只有最终效果截图；把对话整理成段落文字；截图遮住提问或回答 |
| 验收标准 | 评委能在 2 分钟内看出"AI 第一次哪里不对" |
| 拿不出来怎么办 | **不许补造**。一段原始对话都没有的，走"非会话类证据"（技术文档附录 A 的写法），拿不到满分过程分，但不至于被判零分 |

> 详细规范见同目录 `02_AI对话快照模板.md`。

### 材料 3 · 复现性声明与重现指南（README.md）

| 项 | 要求 |
| --- | --- |
| 交付内容 | `03_复现指南/` 下 `README.md`、`.env.example`、`10分钟实测记录.md` |
| 格式 | Markdown + 环境变量模板文件 |
| **硬性下限** | ① 环境配置说明 ② 依赖清单 ③ 环境变量模板（`.env.example` 是文件，不是一句话）④ 两条启动路径（完整 / 最小可跑）⑤ 实测耗时在 10 分钟内 |
| 禁止 | 只有一句话的说明；命令带占位路径无法直接执行；写"大概 3 分钟"这类估算 |
| 验收标准 | 删掉 `.env`、断网之后，最小可跑路径仍然能启动并给出明确降级提示 |
| 拿不出来怎么办 | 10 分钟跑不完的，如实写实测值并说明卡在哪一步。**谎报时间比慢更容易被发现** |

> 模板见同目录 `03_README参赛模板.md`。

| 项 | 要求 |

| 拿不出来怎么办 | 对话记录缺失的，改录"现在做一次真实改动"的全过程。**真实但发生在 11 月，好过伪造在 9 月** |

> 分镜模板见同目录 `04_演示视频脚本模板.md`。

## 五、一条对齐原则（这是整套材料的关键）

三份材料不是独立的，它们必须**互相指认**：

```text
第 N 次关键提交  ←→  第 N 个对话快照案例  ←→  技术文档第 3.N 节
     ↑                                              ↑
  写清楚做了什么                          写清楚哪句话改的
```

具体做法：在 `commit-index.md` 里做一张这样的表：

| 提交 Hash | 时间 | 做了什么 | 对应对话案例 | 对应技术文档 |
| --- | --- | --- | --- | --- |
| `a1b2c3d` | 10-28 | 增加 RAG 资料不足时的拒答分支 | `01_RAG防幻觉` | 3.2 |
| `e4f5g6h` | 11-02 | 工具调用缺参数时先反问 | `02_Agent参数约束` | 3.3 |

**这张表是整套材料里性价比最高的东西。** 评委顺着它一路点下去，三项证据互相印证，25% 的过程分就落地了。
反过来，如果三份材料各说各的，评委会觉得"材料很丰富，但拼不起来"。

## 六、00_提交说明.md 该怎么写

一页纸，不要超过 40 行：

```markdown
# <项目名> 参赛材料说明

**参赛者：** <姓名> <学号>　**组别：** <A / B>
**项目仓库：** <仓库地址>（分支 `<branch>`，标签 `<tag>`）
**仓库可见性：** Public ／ 已授权评审账号 `<账号>`（评委须能直接打开）
**技术栈：** <一句话>

## 材料清单

| 编号 | 材料 | 位置 | 说明 |
| --- | --- | --- | --- |
| 01 | Git 提交日志 | `01_Git提交日志/` | 共 <N> 次提交，跨 <N> 天 |
| 02 | AI 对话快照 | `02_AI对话快照/` | 3 个案例，共 <N> 张截图 |
| 03 | 复现指南 | `03_复现指南/README.md` | 实测 <X> 分 <Y> 秒跑通 |
| 04 | 演示视频 | `04_演示视频/演示视频.mp4` | <N> 分 <N> 秒，AI 协同部分 <N> 分钟 |
| 05 | 技术文档 | `05_技术文档/技术文档.pdf` | <N> 页 |

## 建议评委阅读顺序

1. 先看 `04_演示视频/` 前 30 秒，了解场景
2. 再按 `03_复现指南/` 跑一遍（约 10 分钟）
3. 再看 `02_AI对话快照/01_.../`（约 2 分钟）
4. 最后按需查阅 `05_技术文档/`

## 已知限制

<2-3 条，见技术文档第 7 章>
```

**"建议评委阅读顺序"这一节字数不多，但很有用。** 评委时间很紧，你给他一条路径，他就按你的路径判断；不给路径，他会自己乱翻，可能先翻到最弱的部分。
